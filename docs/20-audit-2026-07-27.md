## Major findings

### M1 - the retired EOF guarantee survives in two places

Commit `918305e` withdrew the universal EOF guarantee: a pre-scan fatal produces **no token stream at all, not even EOF**. Two artifacts still assert the withdrawn rule.

**`v0/src/token/token.ts`**, doc comment on `eofToken`:

> Exactly one is emitted on every path, including an empty file and every fatal error path, so the parser never needs a special case for its absence - docs/02 section 1.9.

It cites section 1.9 while contradicting it.

**`.kiro/specs/01-lexer/tasks.md`**, task 1.12:

> ... the 200 cap (AEG-1006), and the EOF guarantee on every path

**Why no check caught it:** the corpus checker scans for retired *codes* and retired *constructs*. A retired *prose guarantee* is neither. This is a third category of drift with no gate.

**Fix:** correct both. Consider a fourth scan class for withdrawn normative statements, keyed by the commit that withdrew each one.

### M2 - the retired-code and forward-closure scans never read TypeScript

`corpusFiles()` defaults to `[".md", ".aegis", ".json"]`. Both `checkRetiredCodes` and `checkForwardClosure` call it with no argument.

Therefore a file under `v0/src/` may reference a retired code, or a code with no catalogue entry, and every check passes.

This was harmless when there was no code. There are now eight source files and nine test files that name codes as string literals, and `code.ts` contains eighty-four of them. The gap widens with every commit.

**Fix:** extend both scans to `.ts`. Expect the first run to fail; that is the check working.

**Note:** `code.ts` must stay excluded from *reverse* closure, or every code would count as cited and check 8 would assert nothing. Extending the two forward-facing scans and leaving reverse closure on prose is the correct asymmetry, and it deserves a comment saying so.

### M3 - no diagnostic can carry runtime-parameterised text, and five summaries require it

`Diagnostic.summary` is taken from the registry and frozen. `DiagnosticInput` has no field for substitution. There is no mechanism anywhere for a message parameter.

Five catalogue summaries are templates:

| Code | Summary as stored |
| --- | --- |
| `AEG-3070` | `expected X, found Y` |
| `AEG-4010` | `attribute is not declared in any schema (did you mean ...)` |
| `AEG-2040` | `rule is unreachable; here is a witness` |
| `AEG-2050` | `coverage gap; here is a request no rule matches` |
| `AEG-3010` | `circular import (full cycle shown)` |

As written, a renderer prints the literal string `expected X, found Y`.

The traceability test cannot catch this: it asserts byte-identity between `code.ts` and `docs/10`, and both hold the template.

**This blocks task 1.4.** `AEG-1005` needs the offending character in its message, and the delimiter work needs `AEG-3070`'s six tailored shapes.

**Fix, one of:**

1. `summary` stays the invariant catalogue text; parameterised detail moves into `notes` and `helps`, which the caller already supplies. The rendered headline then never varies. Cheapest, and preserves byte-identity.
2. Add an `args` field and a substitution function, with the traceability test asserting that every placeholder in a summary is supplied. More faithful to the rendering standard, more machinery.

Option 1 is recommended, with the five templates rewritten as invariant text.

### M4 - bundle-integrity failures are non-fatal, which contradicts I7

In `code.ts`:

```
entry("AEG-6001", "bad bytecode magic", NOT_FATAL)
entry("AEG-6002", "unsupported bytecode major version", NOT_FATAL)
entry("AEG-6003", "bytecode integrity hash mismatch", NOT_FATAL)
entry("AEG-6010", "bundle signature verification failed", NOT_FATAL)
entry("AEG-6011", "bundle references an unknown signing key", NOT_FATAL)
```

All six fatals in the catalogue are `AEG-0001`, `1001`, `1006`, `1008`, `1009`, `1010` - every one lexical or driver. Not one loader failure is fatal.

I7 is fail-closed. A bundle whose integrity hash does not match, or whose signature does not verify, must stop the pipeline. A non-fatal severity says the loader may continue and evaluate a bundle it has just failed to authenticate.

The amendment recorded that `AEG-6010` and `AEG-6011` carry a fail-closed obligation and may not be downgraded to a warning by configuration. Fatality is the mechanism that enforces it, and it is not set.

**Fix:** mark all five fatal in `docs/10` and in `code.ts`. If the intent was that the loader reports and the *host* fails closed, say so in the catalogue, because the current data says otherwise.

### M5 - `AEG-4013`'s summary contradicts the ruling that defined it

Stored summary:

> Optional binding shadows a keyword, a prelude name, or an enclosing binding

Commit `366a104` established the opposite reading: a repeated name in one `and` chain is `AEG-4013` because a set-union collision is **ambiguity, not shadowing**. There is no enclosing binding to shadow - `binds()` unions siblings.

Undetectable by the traceability test, because `docs/10` carries the same stale text.

**Fix:** resummarise as a duplicate-binding-name collision, in `docs/10` first.

### M6 - `kw.violation` is a keyword with no production

`kind.ts` lists `kw.violation` under Targeting. The obligation form `on violation` was replaced by `on permit` and `on deny`, and triggers are now `permit` and `deny` only.

The checker's retired-construct list does not include `on violation`, and check 2 only asserts that grammar terminals are classified - never that classified keywords are reachable.

This is the orphan-keyword defect class from the P0 audit, recurring.

**Fix:** either delete `violation` from the 77 and drop the count to 76, or name the production that uses it. Then add the inverse of check 2: every keyword in section 1.5 appears as a terminal in the grammar.

### M7 - `kw.to` may be a second orphan

Listed under "Binding and assertion (9)". No production read during this audit uses `to`. Flagged for verification rather than asserted, because the grammar was not read.

The inverse-of-check-2 gate proposed in M6 would settle both M6 and M7 mechanically, and would have caught them before either was written.

### M8 - UTF-8 classes 6 and 7 overlap if section 1.1 reads "F5 through FF"

`sequenceLength` routes `F8`-`FD` to `five-or-six-byte-sequence` and only `FE`, `FF` to `invalid-leader-byte`. Commit `918305e` describes class 7 as "the leader bytes C0, C1, F5 through FF", which would place `F8`-`FD` in both classes.

This is the identical defect to the `C0 AF` collision fixed in `fe8ed2c`, in the adjacent range. The code resolves the ambiguity silently; the specification must state it.

**Fix:** verify section 1.1 enumerates class 7 as `C0`, `C1`, `F5`-`F7`, `FE`, `FF`. If it says "F5 through FF", correct it and record the boundary reasoning as was done for class 3.

### M9 - `truncated-sequence` conflates two different defects

`validateSequence` returns `truncated-sequence` both when the buffer ends mid-sequence and when a continuation byte is absent but bytes remain, as in `E0 41`.

These are different inputs with different fixes. Under the seven closed classes, the second has no name unless class 2 is explicitly defined to cover it.

Codes and defect names are conformance surface. Two implementations reading section 1.1 could disagree.

**Fix:** either state in section 1.1 that class 2 covers any sequence not completed by continuation bytes, or split the defect.

### M10 - `AEG-1009`'s help promises UTF-16 detection it rarely performs

Help text: this file may be binary, or saved as UTF-16.

But a UTF-16 file **with** a byte order mark begins `FF FE` or `FE FF`, both invalid leader bytes, so it fails `AEG-1001` first - the normative order puts UTF-8 validity before the NUL scan. Only BOM-less UTF-16 with ASCII content reaches `AEG-1009`.

A Windows contributor saving as UTF-16 will most often see "invalid UTF-8 byte sequence" with no mention of encoding.

**Fix:** add the UTF-16 hint to `AEG-1001` as well, conditioned on the first two bytes being `FF FE` or `FE FF`.

### M11 - the `;` retired-construct rule will fire on legitimate source

```
{ name: "`;` statement separator", re: /;/ }
```

Any semicolon on any line of any `.aegis` file, or of any aegis-fenced block outside the two excluded directories, fails the build. A semicolon inside a string literal is legitimate. So is one inside an RE2 pattern passed to `matches`.

**This blocks task 1.8**, which must add string-literal cases, and **task 1.13**, which builds one valid case per token kind including `lit.string`.

**Fix:** exclude semicolons inside string literals, or narrow the rule to a semicolon at end of line or before a line comment. The rule is correct in intent - the language has no statement terminator - and wrong in reach.

### M12 - task 1.10 re-claims work task 1.3 already delivered

Task 1.10 reads "the surviving lexical limit checks: AEG-1010 fatal, AEG-1011, AEG-1012". `AEG-1010` was implemented in task 1.3 as the first stage of `admitSource`.

Two tasks owning one check invites a second implementation or a silent skip, and `MAX_SOURCE_BYTES` is now tied by check 10 to the `AEG-1010` row.

**Fix:** remove `AEG-1010` from task 1.10 and note in 1.3 that it owns the size check.

## Minor findings

### m13 - the detection ledger does not exist

Task 1.12 has no ledger of diagnostics that are detected but not yet emitted. `AEG-1007` positions are collected in `buildLineIndex` and consumed by nothing; `AEG-1002` is in the precedence chain with no detector.

Without a ledger, closing 1.12 depends on remembering. Add the ledger and make it an acceptance criterion of 1.12: the task cannot close while an entry is unemitted.

### m14 - `AEG-1011` has no owner in the pipeline

`lineLengthInBytes` exists and computes exactly what `AEG-1011` measures. Nothing calls it. It belongs in task 1.10 and should be a ledger entry until then.

### m15 - freezing is inconsistent, one level deep

`makeSpan` and `makeToken` freeze. `lineColumnAt` returns an unfrozen `{line, column}`. `makeDiagnostic` freezes the diagnostic and copies `secondary` and `specRefs`, but stores `location`, `notes`, and `helps` **by reference**; `atSpan` and `atByteOffset` return unfrozen objects.

A Diagnostic is documented as frozen and is frozen one level deep. Pick one rule and apply it everywhere.

### m16 - `tally()` counts by exclusion

```
if (d.severity === "error") errors += 1;
else warnings += 1;
```

Exhaustive today. Silently wrong the day a severity is added - and `kind.ts` solved this exact problem properly, with a type-guard parameter that makes exhaustiveness a compile error. Two files written hours apart apply different standards to the same hazard.

### m17 - `count()` can exceed the documented maximum

At the cap, `items` holds 200 diagnostics plus `AEG-1006`, so `count()` returns 201 while section 1.2 documents 200. Add one sentence: the cap diagnostic is not counted against the cap.

### m18 - `Code` is typed more loosely than documented

```
export type Code = `AEG-${string}`;
```

The doc comment says "`AEG-` followed by four digits". The type admits `AEG-banana`. A four-digit template literal type is expressible and would make the doc true.

### m19 - `severityOf` tests a string prefix, not a range

`code.startsWith("AEG-2")` works for four-digit codes and silently misclassifies any future five-digit code. Parse the numeric part and compare against the range table.

### m20 - section comments in `check-corpus.mjs` are misnumbered

Two sections are numbered `6` - commit trailers and reverse closure - and the comment sequence runs 1, 2, 3, 4, 6, 6, 9 against a `CHECKS` array of ten entries in a different order. Cosmetic, in the one file whose job is to catch exactly this kind of drift.

### m21 - the checker calls comments inside a fence "prose"

`aegisCodeLines` skips any line matching `^\s*//`, commented as "a comment inside a fence is prose". The language holds the opposite position: comments are trivia that must round-trip byte-exact, and task 1.9 implements them as tokens. Two definitions of one artifact.

### m22 - `checkNumericLimits` takes the first number in a row

`spec?.numbers[0]` is the limit only when the row states one number. A row such as the duration range states two. Correct for the two constants checked today, latent for the third.

## Verified correct

A clean finding is worth as much as a defect, and these were checked rather than assumed.

- **Kind arithmetic closes.** 5+12+11+8+5+17+7+3+9 = 77 keywords; 29 reserved-forbidden; 77+29+4+2+21+4+1 = 138 total. The 21 delimiters match the published set exactly.
- **`categoryOf` is proven total at compile time** by `specialCategory(_kind: "eof")`, without a throw. This is the correct technique and the best single idea in the codebase.
- **UTF-8 leader dispatch boundaries are right:** `C2`-`DF` to 2, `E0`-`EF` to 3, `F0`-`F4` to 4. Both overlong guards (`E0 80..9F`, `F0 80..8F`), the surrogate guard (`ED A0..BF`), and the maximum guard (`F4 90..`) are present and correctly bounded.
- **The absence of a two-byte overlong check is correct**, not an omission: `C0` and `C1` are rejected as invalid leaders before any sequence is validated.
- **`textEndOf` is correct on all four line-ending cases**, including an empty CRLF first line, where the `end > start` guard prevents an underflow past the line start.
- **The `lineOf` and `lineCount` clamp correctly suppresses the phantom final line** for a file ending in a terminator.
- **CRLF and LF produce identical positions.** Traced by hand for a CR at the terminator, an LF at the terminator, and the first byte of the next line.
- **Inclusive maxima are implemented as inclusive.** `source.length > MAX_SOURCE_BYTES`, not `>=`.
- **Live code count is 84**, and the six fatals are the six the catalogue marks.
- **Nothing in the code read iterates object keys to enumerate anything.** `KIND_NAMES` is the ordering authority everywhere, and every `Set` and `Map` is used for membership, never for iteration into output. I2 holds in the code that exists.
- **The trailer parser reads the final block only**, which is what git means by a trailer, and the historical arm uses the same parser.
